## 1. Guiding Principles

This section explains *why* the frontend is shaped the way it is. The sections that
follow describe *what* it does; nearly every mechanism below exists to serve one of
these principles.

### 1.1 The filesystem is the source of truth; the database is a cache

The founding idea. You organize files in `Albums/` with whatever tools you already
use — Finder, Explorer, a shell — and the gallery reflects that. There is no import
step, no upload UI, no "add to library" workflow.

- **The problem this solves.** Other gallery software requires a full import/scan
  before new content appears. Adding five files could mean waiting 30–45 minutes while
  the entire collection is re-imported. That cost is paid on *all* files to surface a
  change to a *few*.
- **The rule.** The database holds nothing that cannot be regenerated by re-reading the
  filesystem. Delete it and browse the tree again, and you are back where you started.
  The sole exception today is **user accounts**. (Future features may add
  non-derivable data — e.g. ownership of uploaded files — but that is a deliberate
  exception, not a loosening of the rule.)
- **Consequence: discovery is lazy, and rescanning is event-driven.** A directory is
  scanned the first time someone visits it — you pay only for what you actually look
  at. After that it stays cached and is *not* re-read on subsequent visits. A rescan
  happens only when the filesystem watchdog observes a change in that directory and
  marks it invalidated. Browsing is cheap; the cost is paid on change, not on access.
- **Consequence: when the two disagree, the filesystem wins.** Content present in the
  database but gone from disk is treated as a stale cache entry — discarded and
  reconciled, never served.
- **Consequence: caches must never outlive the truth.** Caching is what makes
  filesystem-as-truth affordable, so every cache is bound to an invalidation signal
  from the filesystem. Speed never costs correctness.
- **Consequence: attention drives work.** Thumbnail generation for a gallery you are
  looking at takes priority over any background or bulk maintenance work.

**The albums tree is read-only to QuickBBS.** It never deletes, moves, renames, or
creates files there. Curation belongs to the owner/maintainer, using whatever tools
they prefer; the gallery's job is to reflect the result. This is what makes
filesystem-as-truth safe to rely on — the truth is only ever edited from one side.
Everything the gallery derives (thumbnails, index records) is stored in the database,
never written back beside the originals.

**The CLI import is an accelerator, never a requirement.** Any state the command-line
import/verification produces is also reachable by browsing to the same directories. It
exists to avoid the round-trips and mid-request pauses that occur when the web server
absorbs a very large batch of changes — not to unlock anything the web interface
cannot do.

### 1.2 Identical files are the same file

The gallery is modelled on an actual gallery: the same work *can* legitimately belong
in several places at once. Anime filed by series *and* by character; one artist appearing
across multiple topics. Cross-filing is expected and correct, not a mistake to be
cleaned up.

- **Identity is content, not location.** Files are identified by their SHA256. The same
  signature in ten directories is identified as a single file that has been duplicated
  across those ten directories — not ten unrelated files that happen to look alike. The
  filename, the directory it sits in, and the timestamp on disk are all incidental; the
  hash is the only thing that determines whether two entries are "the same file."
- **SHA256 vs. unique SHA256.** The gallery actually keeps two hashes per record, and
  they answer different questions. `sha256` is the hash of the file's bytes alone — it
  is deliberately *not* unique, since every duplicate copy of a file shares it, which is
  what lets thumbnails and derived data be found and reused across copies. `unique_sha256`
  is the hash of those same bytes plus the file's path, giving one guaranteed-unique
  identifier per (content, location) pair. Because it's deterministic rather than random,
  a rescan reproduces the same `unique_sha256` for a file that hasn't moved or changed —
  unlike a UUID, it survives the record being deleted and recreated, so bookmarked and
  shared links keep working. In short: `sha256` answers "is this the same content as
  that other file?"; `unique_sha256` answers "is this the same record I linked to before?"
- **This is primarily work-avoidance, not display preference.** If a file is byte-identical
  to one already processed, there is no reason to generate a second thumbnail or store
  a second copy of the derived data — they *are* the same file.
- **Deduplication is what makes cross-filing safe.** Because the same file can live in
  multiple directories without penalty, the database tracks every location a given
  SHA256 appears in and deduplicates its own records accordingly — one thumbnail, one
  set of derived data, many directory entries pointing back to it. This is what spares
  the gallery from redoing the same work every time a duplicate shows up somewhere new.
- **Showing duplicates is a preference, not the point.** Hiding them is the default,
  since the de-duplicated view is the honest one; seeing every instance is available
  per-user when you want it. Whichever you choose, paging through a gallery and
  stepping through items one at a time present the same content in the same order.

### 1.3 Self-hosted, format-agnostic, cross-platform

- **Self-hosted, and easy to run.** You control the deployment — a machine at home, a
  remote server, a data center, wherever suits you. Ease of setup and low ongoing
  maintenance are explicit goals, not afterthoughts.
- **Content arrives however you already put files somewhere.** SFTP, FTP, Samba, a
  file manager, a sync tool — the gallery does not care. It reads what is on disk
  (§1.1), so any means of getting files there works and none is privileged.
- **Format-agnostic.** Broad file-format support is a deliberate goal, inherited from
  the project's BBS lineage — a bulletin board served whatever people brought to it.
- **Cross-platform.** The server runs on macOS, Windows, and Linux; the client is any
  browser. macOS is the primary development platform and carries some optimizations,
  but the only Mac-only *functionality* is `.alias` file resolution — and `.link` files
  provide the same capability everywhere. Filesystems disagree about filename case, so
  the gallery normalizes rather than assuming any one platform's behavior.
- **A platform-specific shortcut is an accelerator, never a requirement.** Where a
  macOS-native path exists — `.alias` resolution, GPU-backed rendering — a
  cross-platform equivalent produces the same result through ordinary means. The
  accelerated path is free to be faster or cheaper; it is never the only way to get a
  correct answer, and nothing may assume it is present.

### 1.4 Only the current page is ever loaded

Directories may hold thousands of files, so the cost of displaying a page must depend
on the size of the page, not the size of the directory. Gallery listings and search
results alike retrieve only what the current page shows. Nothing loads a whole
directory to display twenty items.

### 1.5 Browsing should feel continuous

Viewing a large collection means moving constantly — into a directory, through its
pages, into an item, on to the next. Reloading a full page for each of those movements
is both slow and disorienting.

The gallery is therefore built to swap only the part of the page that changed, which
made it behave much more like a single-page application and cut out the large amount
of state that previously crossed the wire on every navigation. Full pages are still
served when they are genuinely wanted — a direct link, a new tab, a fresh load — so
opening something in a new window yields a real, complete page rather than a fragment.

Continuity also extends to not losing your place: moving between a gallery and an
individual item is intended to preserve where you were.

### 1.6 Read-only keeps the threat model small

Because the gallery only reads the albums tree and accepts no uploads (§1.1), the
realistic risks today are **hardware failure** and **someone gaining filesystem access
they should not have** — not attacks arriving through the application. There is no
write path for a request to abuse.

This is partly *why* uploads do not exist yet. Accepting them means introducing
per-file ownership and the controls that let each owner manage their own files without
touching anyone else's. That is a question of scale and correctness, not of effort, and
it is deferred until it can be done properly. Adding uploads therefore also means
revisiting this principle and §1.1's derivable-data rule together.

None of that excuses careless input handling. Requests still carry untrusted data —
paths, search terms, filenames destined for headers — and every one of those is
validated and constrained before use. The point is that the blast radius of a mistake
is currently bounded by having nothing to write to.

### 1.7 Scope is set by real use, not feature parity

QuickBBS exists to view a gallery well. Features are added when the author needs them,
not to match what comparable software offers.

Tagging, richer metadata, ratings, comments, and in-gallery editing are all recognized
as useful and have been considered — none is rejected on principle. They have simply
not been added yet, because viewing is the goal and the current feature set is good
enough for it. Read their absence as *not yet needed*, rather than as a deliberate
exclusion.

### 1.8 Degrade to something sensible before failing

Safety first, where possible. When a request carries bad or unusable input but the
intent is still clear, the gallery falls back to a sensible default rather than
refusing to answer:

- Asking for a page beyond the end of a gallery shows the last real page, not an empty
  one.
- A search the database cannot execute as written falls back to a simpler match rather
  than failing the search.
- A single unreadable file is skipped during a directory scan; one bad entry does not
  blank the gallery around it.

This is not error-hiding. When there is no sensible interpretation — a directory that
does not exist, a path outside the albums tree, a download with no identifier — the
request gets a proper 404 or error response. The rule is to degrade when intent is
recoverable and fail clearly when it is not.

## 2. Purpose

`frontend` is the Django application that handles all HTTP request/response logic for
the QuickBBS gallery. It owns:

- **Views** — gallery listing, item viewer, search, file download, and administrative
  reports
- **Layout management** — database-level pagination of directory/file content
- **File serving** — HTTP file delivery, byte-range streaming for video, static/resource
  serving
- **Directory scanning** — filtered filesystem directory listings
- **Path utilities** — filesystem-to-web-path conversion and breadcrumb generation

**Concurrency model:** views are plain synchronous `def` functions. Django adapts them
transparently under ASGI, running each in a thread from the handler's thread pool with
`thread_sensitive` semantics that keep Django ORM usage safe. The single exception is
`download_file()`, which stays `async def` because it streams file bytes and gains a
real benefit from not occupying a worker thread for the duration of a large transfer.

This is a deliberate reversal of the previous design (v4.00), where every view was
`async def` with `sync_to_async()` wrappers around each DB/filesystem call. That
pattern produced many async/sync boundary crossings per request for no measurable
gain, since the underlying work was database-bound rather than I/O-concurrent.

## 4. Component Reference

### 4.1 `apps.py`

**What does this do?** Makes sure the image-handling library is set up correctly
before the gallery tries to use it, rather than leaving each caller to configure it
on its own.

**What is its purpose?** `AppConfig` subclass whose `ready()` calls `configure_pil()`
(from `quickbbs.settings`) to set PIL/Pillow global options before any image
operations can occur.

---

### 4.2 `views.py`

**What does this do?** Answers every page and file request a visitor actually makes —
browsing a directory, viewing a single item, searching, and downloading — the module a
request lands in first.

**What is its purpose?** The entry point between the web server and the rest of the
app: every view here takes an incoming HTTP request and turns it into a response,
dispatching to the models and helpers that do the actual work rather than doing that
work itself.

---

#### `view_gallery(request)`

**What does this do?** Shows a user the contents of a directory, one page at a time.
This is the view most requests hit, so it has to feel instant even on a directory with
thousands of files.

**What is its purpose?** Primary gallery view: turns a URL path into one page of a
directory's contents.

Resolves the requested path to a directory, creating or updating the database record as
needed when the directory is visited, and renders a single page of its subdirectories
and files. Directories come first, then shortcuts, then regular files — a consistent
order that item-view navigation also follows.

Only the current page is ever loaded. The cached layout supplies the identifiers
belonging to this page, and just those rows are hydrated; a directory of ten thousand
files costs the same as one holding twenty. If any files on the page still lack
thumbnails, that work is enqueued *after* the layout is read, so generating thumbnails
never invalidates the layout that requested them.

Repeat visits are cheap: the listing, its ordering, and its counts all come from caches
that hold until the filesystem watchdog reports a change.

**Request flow:**

```
 1. _get_show_duplicates_preference() — user pref from TTL cache or DB
 2. _determine_template() — partial vs full page based on request.htmx
 3. Decode and normalize request.path (unquote, lowercase, os.sep → "/")
 4. _find_directory() — DB lookup/create/validate, with albums-root containment check
 5. update_database_from_disk() — sync directory contents with filesystem
 6. _create_base_context() — shared base dict
 7. layout_manager() — paginated SHA lists (cached)
 8. get_prev_next_siblings() — prev/next directory URIs
 9. dirs_in_dir() filtered by layout SHA list — annotated with file/dir counts
10. files_in_dir() filtered by layout SHA list — split into files + links
11. _check_and_enqueue_missing_thumbnails() — enqueue thumbnail tasks
12. render() with the Jinja2 engine
13. Set Cache-Control: private, no-cache, must-revalidate for authenticated users
14. snapshot_cache_statistics() if CACHE_MONITORING is enabled
```

**Item ordering on page:** shortcuts are identified by `filetype.is_link`; files and
links are split from a single fetched list rather than queried separately.

**Thumbnail enqueueing:** priority 50 (vs priority 0 for bulk maintenance tasks), batch
size `settings.THUMBNAIL_BATCH_LIMIT`.

---

#### `htmx_view_item(request, sha256)`

**What does this do?** Shows one file full-size, and lets a user step to the next or
previous file in the same directory without losing their place.

**What is its purpose?** Single-item viewer: shows one file full-size, with the rest of
its directory reachable as previous/next/first/last.

Everything the page needs — the file's metadata, its rendered content, and where it
sits among its neighbours — is assembled by `build_context_info()` from the same
ordered lists the gallery pages from. That shared ordering is the point: stepping
through items one at a time visits them in exactly the order the gallery displayed
them, and the item view knows which gallery page to send you back to.

Position is resolved by list arithmetic over cached data rather than by querying for
neighbours, so navigating within a directory issues few or no queries after the first
item. If files in the same directory still lack thumbnails, a small batch is enqueued
while you are looking — the directory you are browsing gets prioritized over background
work.

**Request flow:**

```
1. _get_show_duplicates_preference()
2. _determine_template() — item partial vs full page
3. build_context_info() — navigation context from managers.py
4. _check_and_enqueue_missing_thumbnails() — warms thumbnails for the item's
   directory at settings.ITEM_VIEW_THUMBNAIL_BATCH_LIMIT
5. render() with the Jinja2 engine
```

`build_context_info()` may return an `HttpResponseBadRequest` instead of a context
dict (empty or unresolvable SHA); the view returns it directly.

Uses the `DirectoryIndex` carried in the `build_context_info` context
(`context["home_directory"]`) rather than re-fetching it, avoiding a redundant DB
round-trip.

---

#### `search_viewresults(request)`

**What does this do?** Lets a user find something by name across the whole
collection, instead of having to already know which directory it's in.

**What is its purpose?** Search view: finds directories and files whose names match
the search text, and presents the combined results as one paginated listing.

Matching is separator-agnostic — spaces, underscores, and dashes are treated as
interchangeable, so `black cat`, `black_cat`, and `black-cat` all find each other.
Directory names and file names are searched independently and the two result sets are
concatenated, directories first, mirroring how a gallery page is laid out.

Searches run against the whole database rather than one directory, so the same
only-load-the-current-page discipline applies and matters more: the result set is
counted, the requested page is clamped into range, identifiers for that page alone are
fetched, and only those rows are hydrated. A search matching fifty thousand files
costs the same to render as one matching thirty.

Two things are deliberately withheld here. No check for missing thumbnails is
performed for search results, since that check would mean scanning the entire
collection rather than one directory a user is looking at — a thumbnail still gets
created the normal way, if it doesn't already exist, when an item is actually viewed.
And results are never cached by the browser or by HTMX history, so a second search
cannot show the first one's results.

**Two-phase query pattern:**

1. `_get_paginated_search_results()` — COUNT dirs and files; clamp the requested page
   into `1..total_pages`; compute `calculate_page_bounds()`; fetch only SHA values for
   the current page using LIMIT/OFFSET slices. This phase passes empty prefetch tuples
   and `include_annotations=False`, so the sliced query stays a plain filtered scan
   with no LEFT JOIN/GROUP BY.
2. Hydrate full objects for this page only via `__in` lookups with `prefetch_related`
   and `annotate` (file/dir counts).

This mirrors the `layout_manager` pattern: only current-page data is ever loaded.

**Page clamping** happens inside `_get_paginated_search_results()` *before* slicing, so
an out-of-range page (`?page=999` on a 3-page result) returns the last page's items
rather than an empty slice with a valid-looking page bar. The caller recomputes the
same clamp for the context values it renders.

**Cache behaviour:** response headers force `no-store, no-cache, must-revalidate,
max-age=0` plus `Pragma: no-cache`, `Expires: 0`, and `HX-Replace-Url: false` to
prevent HTMX history caching and browser caching from showing stale results on
subsequent searches.

**Thumbnails:** `context["files_needing_thumbnails"]` is set to `FileIndex.objects.none()`
— an empty queryset rather than an empty list, keeping the context type consistent with
the gallery view.

**`create_search_regex_pattern(text)`** escapes the input, then converts escaped
spaces, underscores, and dashes to `[\s_-]+` for separator-agnostic matching. Returns
`""` for empty input or when the resulting pattern exceeds 500 characters (ReDoS cap);
an empty pattern makes `get_search_results()` return empty querysets.

**`_safe_regex_search()`** performs the `__iregex` query and falls back to `__icontains`
if the database rejects the regex.

---

#### `download_file(request)`

**What does this do?** Lets a user download a file or watch a video, including
scrubbing to any point in it, without the gallery choking on a large transfer.

**What is its purpose?** Delivers the actual bytes of a file — a download, or a video
played inline in the browser — rather than a page describing it.

This is the one view that stays asynchronous, and the only one where that earns its
keep. Serving a large video means holding a connection open for as long as the viewer
watches; doing that synchronously would occupy a worker thread for the entire duration.
Streaming it asynchronously means a slow or long-running transfer costs a connection
rather than a thread, so downloads cannot starve the rest of the gallery.

Video is served with byte-range support, which is what makes seeking work: a browser
scrubbing to the middle of a file requests only that range, and only that range is
read and sent. Files are streamed in chunks and never loaded into memory whole,
regardless of size.

A viewer who navigates away mid-download disconnects, which is normal rather than an
error — the resulting cancellation is passed through for cleanup without being logged
as a failure.

The requested file is identified by content hash rather than by path, so a download URL
stays valid regardless of which directory the file is being viewed from.

**Mechanism:** takes `unique_sha256` as `?usha=` (or `?USHA=`), normalized via
`normalize_sha_input()`. The row is looked up through
`sync_to_async(FileIndex.get_by_sha256_for_download)` — the only explicit
`sync_to_async` call left in the view layer — then handed to
`FileIndex.async_inline_sendfile()`, which chooses between an async ranged streaming
response (videos) and a `RangedFileResponse` over a `SizedFileWrapper` (everything
else). `asyncio.CancelledError` is re-raised without logging.

Raises `Http404` when no identifier is supplied or no matching file exists.

#### Helper functions in `views.py`

| Function | Description |
|---|---|
| `_determine_template(request, template_type)` | Returns partial or complete Jinja2 template path. Partial when `request.htmx` is truthy and `?newwin=` is not set |
| `_create_base_context(request)` | Builds shared context dict (debug flag, sort, current page, image sizes, user, `fromtimestamp`, empty placeholder lists) |
| `get_page_param(request)` | Reads `page` from POST then GET; returns `max(1, int(value))`, or 1 for missing/non-numeric input |
| `_find_directory(paths)` | Validates the path is inside the albums tree, looks up `DirectoryIndex` by SHA, creates via `add_directory()` if missing, re-validates the physical path, invalidates parent cache on creation |
| `_check_and_enqueue_missing_thumbnails(directory, sort_ordering, batch_limit)` | Gets files needing thumbnails, enqueues `generate_missing_thumbnails` at priority 50; returns the count enqueued |
| `_get_show_duplicates_preference(request)` | Reads `UserPreferences.show_duplicates`; caches in `_user_pref_cache` keyed on `user.pk`; returns `False` for anonymous users |
| `create_search_regex_pattern(text)` | Separator-agnostic regex builder (see above) |
| `_safe_regex_search(...)` | Regex query with `icontains` fallback, plus optional prefetch/annotate/order |
| `get_search_results(...)` | Builds the directory and file search querysets |
| `_get_paginated_search_results(...)` | Page-clamped, COUNT-then-slice SHA fetch for search |

`get_sort_param()` lives in `frontend/utilities.py` and is imported by `views.py`.

**`_user_pref_cache`** is a module-level `ThreadSafeTTLCache` (from
`quickbbs.MonitoredCache`) sized by `settings.USER_PREF_CACHE_SIZE` with
`settings.USER_PREF_CACHE_TTL`. The thread-safe variant matters because sync views run
concurrently across the ASGI handler's thread pool. It is explicitly cleared by
`user_preferences/views.toggle_show_duplicates()` when the user changes their
preference.

**Exceptions:** `DirectoryNotFoundError` (physical directory missing → 404) and
`DirectoryInvalidError` (invalid/escaping path → 400) are defined here and caught in
`view_gallery()`.

### 4.3 `managers.py`

**What does this do?** Figures out what belongs on the page a user is looking at, and
where a single file sits relative to the rest of its directory, so both the gallery
and the item viewer agree on the same order.

**What is its purpose?** Layout and context building: computes paginated
directory/file listings and single-item navigation context, shared by the gallery,
item viewer, and search views.

#### `layout_manager(page_number, directory, sort_ordering, show_duplicates)`

**What does this do?** Works out what a user should see on a given gallery page,
cheaply enough to do it on nearly every visit to a directory.

**What is its purpose?** Answers *what belongs on this page of this directory*.

A gallery page shows subdirectories and files as a single sequence — directories first,
then files — even though the two are stored separately. This function works out how
that sequence divides into pages, and returns the identifiers of the items falling on
the requested one, along with the page count and the page number to use for the "back"
link.

Only identifiers are returned, never objects. The caller fetches the rows it needs from
those identifiers, so a directory's size affects the cost of paging through it hardly
at all. Files come from a cached ordered list — the same list the item viewer navigates
— so slicing a page out of it is list arithmetic rather than a query. Directories are
sliced in the database, since a directory's children are usually few.

The result is cached per page, per directory, per sort order, and per duplicate
setting, and stays valid until the filesystem watchdog reports a change in that
directory. This is the cache that makes repeat gallery visits nearly free.

**Caching:** via `layout_manager_cache` (from `quickbbs.cache_registry`); the key is
built by `_layout_manager_key()` as
`hashkey(page_number, directory.pk, sort_ordering, show_duplicates)`.

**Why `directory.pk` and not the `DirectoryIndex` object?**  
`clear_layout_cache_for_directories()` in `cache_registry` invalidates entries with a
direct integer comparison on `key[1]`. Using the full ORM object would require
identity/equality comparisons, which are fragile across different query paths that
load the same row.

**Pagination algorithm:**

```
dirs_count  = directory.get_dir_counts()                  # dir_counts_cache
all_shas    = get_all_file_shas(sort)      if show_duplicates
              get_distinct_file_shas(sort) otherwise      # cached ordered SHA lists
files_count = len(all_shas)
total_items = dirs_count + files_count
total_pages = max(1, ceil(total_items / GALLERY_ITEMS_PER_PAGE))

calculate_page_bounds(page, GALLERY_ITEMS_PER_PAGE, dirs_count):
  → dirs_slice:  (start, end) into the directory queryset
  → files_slice: (start, end) into the cached SHA list

Fetch:
  - directory SHAs via queryset LIMIT/OFFSET (database paging)
  - file SHAs via a plain list slice of the cached ordered SHA list (no DB query)
```

Both the duplicate and de-duplicated modes read a cached ordered SHA list owned by
`DirectoryIndex`. `build_context_info()` reads the *same* lists, so gallery page order
and item-view prev/next agree even for rows with tied sort keys.

**`page_locale`** — the page number within the parent directory where _this_
directory would appear (used for the "back" link). Computed from
`get_ordered_sibling_dirs(directory.parent_directory_id, sort_ordering)`
(`sibling_dirs_cache`, shared with `get_prev_next_siblings`). The check reads
`parent_directory_id` — Django's *attname* for the FK, the raw column value already
sitting in memory — rather than `parent_directory`, which would trigger a database
query to lazy-load the parent row. Defaults to 1 for root directories or when the
directory is not found among its siblings.

**`files_needing_thumbnails` is not part of the output.** It is computed separately by
the caller so thumbnail generation does not invalidate the cached layout.

- **Deprecated output keys**, commented out in place pending removal after 2026-06-01:
  `chunk_size`, `dirs_on_last_page`, `files_on_last_page`, `page_shas`.
- There is no `async_layout_manager` wrapper any more — sync views call
  `layout_manager()` directly.

#### `build_context_info(unique_file_sha256, sort_order_value, show_duplicates)`

**What does this do?** Gives a user, from a single file's identity, everything the
single-item view needs: the file itself, plus where it sits relative to the rest of
its directory.

**What is its purpose?** Assembles everything the single-item page needs, from one
file identifier.

That means two kinds of information. First, the file itself: its metadata, the HTML
used to display it, breadcrumbs, and URLs for downloading it and for its large
thumbnail. Second, and less obviously, where it sits among its neighbours — which item
is first, last, next, and previous, what position this one occupies, and how many
there are in total.

Neighbours are resolved from the directory's cached ordered list of file identifiers
rather than by querying for them. Finding the current item's position is a list search,
and its neighbours are the entries on either side. Since that is the same list the
gallery pages from, item-by-item navigation follows exactly the order the gallery
displayed — including for files whose sort keys tie, where a fresh query could
legitimately return a different order each time.

The same list also yields the gallery page this item appears on, which is what lets the
item view offer a "back" link that returns you where you came from instead of to the
top of the directory.

Nothing here is cached as a whole, but every expensive lookup reads through a cache, so
moving between items in one directory typically issues no queries at all.

Returns `HttpResponseBadRequest` when no SHA is provided or no matching `FileIndex`
row exists.

**Duplicate-aware navigation:** both branches have the same shape — fetch the
`(directory, sort)`-keyed cached SHA list once, then resolve position, prev, and next
with list arithmetic.

- `show_duplicates=False` (default): `directory.get_distinct_file_shas(sort)`
  (`distinct_files_cache`).
- `show_duplicates=True`: `directory.get_all_file_shas(sort)` (`all_files_shas_cache`).

Both branches resolve position, prev, and next by list arithmetic over one of these
cached lists — never by issuing a query for neighbours. That matters most for files
whose sort keys tie: a fresh query could legitimately return a different order each
time for tied rows, but reading from the same cached list `layout_manager()` pages
from guarantees item-view navigation order always matches gallery page order, tie or
no tie.

The caches involved are `fileindex_cache` (via `FileIndex.get_by_sha256`), the SHA-list
caches above, and `dir_counts_cache`.

`context["home_directory"]` carries the resolved `DirectoryIndex` so `htmx_view_item()`
can enqueue thumbnails without re-fetching it. Staleness is acceptable because
`files_in_dir()` issues a fresh query through the FK relationship.

- **Deprecated context keys**, commented out in place pending removal after
  2026-06-01: `filetype_icon_filename`, `dir_link`.
- There is no `async_build_context_info` wrapper any more — `htmx_view_item()` calls
  `build_context_info()` directly, passing `get_sort_param(request)`.

#### `calculate_page_bounds(page_number, chunk_size, dirs_count)`

**What does this do?** Makes sure a page shows the right mix of directories and files
even though a gallery page displays them as one seamless list.

**What is its purpose?** Works out where a page falls across two sequences —
directories, then files — that are stored separately but displayed as one.

Directories are listed before files, so any given page may hold only directories, only
files, or the tail of the directories followed by the head of the files. This function
does that arithmetic and nothing else — pure, no I/O, no knowledge of what is being
paged — which is why both gallery listings and search results use it unchanged.

Given a page number and the total directory count, it returns slice boundaries for
directories and files:

- Pages that straddle the dirs/files boundary have both a `dirs_slice` and a
  `files_slice`.
- Pure-directory pages have only `dirs_slice`.
- Pure-file pages have only `files_slice` (with offset adjusted by `dirs_count`).

Returns `None` for a slice when that type has no items on the current page. Also
returns `dirs_on_page`. Shared by `layout_manager()` and
`_get_paginated_search_results()`.

#### `_get_files_needing_thumbnails(directory, sort_ordering)`

**What does this do?** Finds which files in a directory still need a thumbnail, kept
as a separate question so the answer doesn't get frozen into the cached page layout.

**What is its purpose?** Thin delegation to
`ThumbnailFiles.get_files_needing_thumbnail_shas()`.

### 4.4 `serve_up.py`

**What does this do?** Gets bytes out of the gallery and into a browser correctly,
whatever they are — a thumbnail, a full download, or a video being scrubbed through —
without every caller having to reimplement the details.

**What is its purpose?** File delivery: the shared response-building and streaming
functions used to serve thumbnails, downloads, inline media, and the gallery's own
static assets.

#### `send_file_response(filename, content_to_send, mtype, attachment, expiration, request)`

**What does this do?** Makes sure every file that leaves the gallery — a thumbnail, a
download, inline media — gets the same correct handling, instead of each caller having
to get the details right on its own.

**What is its purpose?** The shared exit point for file content leaving the
application. Thumbnails, downloads, and inline media all pass through here, so the
headers that matter get set in one place rather than at each call site: how long the
response may be cached, whether the browser should display or save it, and what
filename to use.

Two details are deliberate. Filenames are sanitized before entering the
`Content-Disposition` header, since a filename comes from the filesystem and can
contain characters that would otherwise let it break out of the header. And `ETag`
generation is suppressed, because computing one means reading the entire file — an
unacceptable cost on large media, and redundant when responses already carry explicit
cache lifetimes.

- Without `request`: returns a plain `FileResponse`.
- With `request`: returns a `RangedFileResponse` (byte-range support for video seek).
- Always sets `Cache-Control: public, max-age={expiration}` (default 300).
- Always strips `ETag` to avoid `ConditionalGetMiddleware` overhead on large files
  (computing ETags requires reading the full content).
- Filename is sanitized via `sanitize_filename_for_http()` before being placed in
  `Content-Disposition`.

**Note on file handle lifecycle:** callers must _not_ use context managers for file
handles passed to this function — Django's `FileResponse` closes the handle after
streaming.

---

#### `build_async_ranged_response(request, path, file_size, content_type, filename, expiration)`

**What does this do?** Lets a user scrub to any point in a video and have it start
playing there immediately, whether the file is two megabytes or two gigabytes.

**What is its purpose?** Streams video in a way that supports seeking without loading
the file into memory.

When a browser plays a video it does not fetch the whole file — it asks for the portion
it needs, and asks again whenever the viewer scrubs to a new position. This function
serves those partial requests: it reads only the requested span, in chunks, and reports
back which span it sent so the browser can position the playhead correctly. A
two-gigabyte file and a two-megabyte one cost the same in memory.

A request with no range, or one that cannot be satisfied as written, is answered with
the whole file as a stream rather than an error — the viewer still gets their video
(§1.8).

Returns a `StreamingHttpResponse` backed by `_async_file_range_iterator` (an `aiofiles`
async generator yielding `RANGE_CHUNK_SIZE` = 64 KB chunks). Used by
`FileIndex.async_inline_sendfile()`.

Supports both full-file (`200 OK`) and byte-range (`206 Partial Content`) requests, and
always sets `Accept-Ranges: bytes` and an explicit `Content-Length`. The Range header
is parsed by `_parse_range_header()`, which handles suffix form (`bytes=-N`) but
rejects multipart ranges (browsers never send them for video); an unparseable or
unsatisfiable header degrades to a streaming 200 rather than a 416.

Responses from this function are excluded from compression — see
`quickbbs/middleware/compression.py`.

---

#### `SizedFileWrapper` / `open_sized_file(path)`

**What does this do?** Avoids making the server read an entire large video just to
find out how big it is.

**What is its purpose?** Tells the range-response machinery how big a file is, so it
does not have to find out the expensive way.

Serving a byte range requires knowing the file's total size. Given a bare file handle,
the underlying library determines that by reading the entire file and measuring the
result — which for a large video means loading gigabytes into memory purely to learn a
number the operating system already knows. Wrapping the handle with its size attached
avoids the read completely.

`open_sized_file()` is the factory: opens the path in binary mode and populates `.size`
from `os.fstat`. Used by `FileIndex.inline_sendfile()`.

---

#### `static_or_resources(request, pathstr)`

**What does this do?** Makes sure the gallery's own look and feel — its CSS, scripts,
icons — loads correctly, and that an edit to one of those files actually takes effect
instead of silently being overridden by a stale copy.

**What is its purpose?** Serves the gallery's own assets — stylesheets, scripts,
icons — as opposed to the content being displayed.

Two directories hold such files: `resources/` for assets belonging to this project, and
`static/` for those supplied by Django and third-party packages. A single view serves
both, and when the same path exists in each, the project's own copy wins. That order
matters in practice: a stale copy left behind in `static/` by an earlier build would
otherwise silently override an edit made in `resources/`, producing a change that
appears not to take effect. When the situation arises the duplicate is reported rather
than passed over quietly.

Because the requested path comes from the URL and may contain traversal sequences, each
candidate is fully resolved and confirmed to still lie within its intended directory
before anything is opened. Responses carry a cache lifetime and a modification date, so
repeat requests can be answered without resending the file.

**Lookup order — `resources/` first.** `_locate_static_or_resource_file()` checks
`settings.RESOURCES_PATH` before `settings.STATIC_ROOT`, so custom assets always win.
If the same relative path exists in both, the `static/` copy is treated as a stale
collectstatic artifact: the `resources/` copy is served and a duplicate warning is
logged and printed.

> This is a reversal of the v4.00 behaviour, where `STATIC_ROOT` was checked first and
> could silently shadow edits made under `resources/`.

**Path traversal defence.** `pathstr` arrives through a `<path:>` URL converter that
permits `..` and `/`, and Django does not collapse `..` segments — a request sent with
raw `..` (e.g. `curl --path-as-is`) would otherwise let `os.path.join` escape the
intended roots. `_safe_join()` resolves each candidate with `os.path.realpath` and
returns `None` unless the result is still under the base directory.

**Caching.** Sets `Cache-Control: public, max-age={settings.STATIC_ASSET_CACHE_MAX_AGE}`
and a `Last-Modified` header so `ConditionalGetMiddleware` can answer repeat requests
(e.g. from an "open in new window" navigation) with a 304.

Raises `Http404` when `pathstr` is `None` or the file is not found under either root.

- An `async_static_or_resources` variant existed previously (read the full file with
  `aiofiles`, wrap it in `BytesIO`) but was never wired into `urls.py` and was removed
  as dead code (2026-07-27, async-simplification Phase 4).

---

#### `sanitize_filename_for_http(filename)`

**What does this do?** Stops a maliciously or oddly named file on disk from being
able to tamper with the HTTP response sent back to a browser.

**What is its purpose?** Strips control characters (0x00–0x1F, 0x7F) and angle brackets, and replaces semicolons
with underscores, to prevent HTTP header injection in `Content-Disposition`. Uses a
pre-computed `str.maketrans` table (faster than regex). Returns `"download.bin"` if
the result is empty.

### 4.5 `file_listings.py`

**What does this do?** Looks at what's actually in a directory on disk and decides
which of those entries the gallery should care about.

**What is its purpose?** Directory scanner: reads a directory from disk with the
filesystem-to-gallery filtering rules applied, and returns the result the gallery's
database sync relies on.

#### `return_disk_listing_sync(fqpn)`

**What does this do?** Answers the question of what content is in this directory that
the gallery is interested in.

**What is its purpose?** Reads a directory from disk and reports what the gallery
should consider to be in it.

This is the point where the raw filesystem contents enter the gallery, and the list it
returns is already filtered — not a plain directory listing. Entries the gallery is
configured to ignore, or does not recognize as a usable file type, are left out before
anything else sees the result. Subdirectories are included in the listing too, tagged
as directories rather than files.

Names are normalized on the way out, because filesystems disagree about filename case
and the same directory must produce the same keys on every platform.

An entry that cannot be read is skipped rather than aborting the scan — one
permission-denied file does not blank the directory around it. A directory that cannot
be read at all reports failure rather than an empty listing, so a transient error is
never mistaken for "everything was deleted" (§1.8).

**This is the function the codebase actually calls.** `quickbbs/directoryindex.py`
imports `return_disk_listing_sync` directly for `update_database_from_disk()`. It
returns `(success: bool, data: dict)`, where `data` maps a title-cased filename (via
`normalize_string_title`) to a `pathlib.Path`; `(False, {})` signals
`FileNotFoundError`, `NotADirectoryError`, or `OSError`.

**Filtering rules (from settings):**

| Setting | Effect |
|---|---|
| `EXTENSIONS_TO_IGNORE` | Skip files with these extensions |
| `FILES_TO_IGNORE` | Skip files with these exact names (lowercase) |
| `IGNORE_DOT_FILES` | Skip any file/dir starting with `.` |
| `filetypes.filetype_exists_by_ext` | Skip files with unrecognised extensions |

Directories are assigned the synthetic extension `.dir`; extensionless files get
`.none`. Per-item `OSError`/`PermissionError` is swallowed so one unreadable entry does
not abort the scan.

---

#### `return_disk_listing(fqpn, **kwargs)` — async wrapper

**What does this do?** Keeps an async door open to the same directory scan, in case a
future caller needs one — nothing in the codebase currently uses it.

**What is its purpose?** `async def` that delegates to
`asyncio.to_thread(return_disk_listing_sync, fqpn)`.
`return_disk_listing_async` is an alias for it. Accepts and ignores legacy `**kwargs`
(`use_async`, `batch_size`, `max_workers`).

> **No current callers.** With views now sync, nothing in the codebase awaits this
> wrapper — `directoryindex.py` uses `return_disk_listing_sync` directly. It remains
> as the async entry point for any future caller that needs one.

### 4.6 `utilities.py`

**What does this do?** Handles the small, easy-to-get-wrong conversions — turning a
disk location into a working link, building the trail of links back to a parent
directory — so every other part of the gallery does them the same way.

**What is its purpose?** Path helpers: filesystem-to-web-path conversion, breadcrumb
generation, sort-parameter validation, and string normalization used across the
views.

Declares `__all__ = ["convert_to_webpath", "ensures_endswith", "get_sort_param",
"return_breadcrumbs"]`. All functions are synchronous.

#### `get_sort_param(request)`

**What does this do?** Figures out what order a user wants their gallery sorted in,
falling back to a sensible default if the request doesn't say or says something invalid.

**What is its purpose?** Reads `?sort=`, validates it against `SORT_MATRIX` keys, and returns
`settings.DEFAULT_SORT_ORDER` for a `None` request or any invalid/non-numeric value.
**Moved here from `views.py`** so `managers.py` and the views can share one
implementation.

---

#### `convert_to_webpath(full_path, directory=None)`

**What does this do?** Makes sure a page never links to a broken or malformed URL by
refusing to guess when a path doesn't fit where it's expected to.

**What is its purpose?** Translates a location on disk into the URL that reaches it.

Every path the gallery handles internally is absolute, rooted in the albums directory,
while every path it puts in a page is relative to the site. This is the one conversion
between the two, and it is deliberately strict: a path that does not start where it
should is an error rather than something to be patched up, since silently emitting a
malformed URL would be harder to diagnose than failing outright.

Raises `ValueError` if `directory` is an empty string, or if the expected prefix is not
present in `full_path`. The albums prefix is pre-lowercased at module load into
`_ALBUMS_PATH_LOWER`.

Cached in `webpaths_cache`, built by `create_cache(settings.WEBPATHS_CACHE_SIZE,
"webpaths", monitored=settings.CACHE_MONITORING)`.

---

#### `return_breadcrumbs(uri_path)`

**What does this do?** Builds the trail of clickable links at the top of a page that
lets a user jump back to any parent directory.

**What is its purpose?** Splits a URI path on `/` and builds a list of `{"name": part, "url": cumulative_path}`
dicts, URL-encoding each component with `urllib.parse.quote(p, safe="")`. Cached in
`breadcrumbs_cache` (size from `settings.BREADCRUMBS_CACHE_SIZE`).

---

#### `ensures_endswith(string_to_check, value)`

**What does this do?** Keeps directory paths consistent so the rest of the code
doesn't have to guess whether a trailing slash is there or not.

**What is its purpose?** Adds `value` as a suffix if not already present. Used to
normalize directory paths to ensure trailing slashes.

### 4.7 `report_views.py`

**What does this do?** Shows an administrator which content is duplicated the most
across the whole collection, mainly as a way to double-check that duplicate detection
is working as intended.

**What is its purpose?** Administrative reports: currently a single deprecated
proof-of-concept view surfacing cross-filed content by SHA256.

#### `duplicate_files_report(request)`

**What does this do?** Shows which content is cross-filed the most, and everywhere it
lives.

**What is its purpose?** Lists files whose content appears many times across the
collection, and where each copy lives.

Since files are identified by content (§1.2), it is possible to ask which content is
most heavily cross-filed. This report answers that: content appearing more than five
times, ordered by how often, with the directory holding each copy. Two queries do the
work regardless of result size — one to find the heavily duplicated content, one to
locate every copy of it — rather than a lookup per group.

Routed at `reports/duplicate_files.html`; renders `reports/duplicate_files.jinja`.
Files pending deletion are excluded.

> **Status: deprecated proof-of-concept.** This report was written to validate the
> SHA-based duplicate-detection system (§1.2), not as a feature for ongoing use. A high
> duplicate count is *not* a problem to act on — cross-filing the same file into many
> directories is normal and expected, and de-duplication already prevents the redundant
> work. The report is retained only because it may be useful for debugging the SHA
> identity logic.

---

#### `_get_duplicate_sha_data()`

**What does this do?** Gathers the raw numbers the duplicate report is built from.

**What is its purpose?** Two queries:

1. Aggregate `file_sha256` values with `COUNT > 5`, ordered by count descending.
2. All matching `FileIndex` rows with `home_directory` joined, fetched via `.values()`
   and grouped by SHA into a `defaultdict`.

Returns `{"groups": [...], "total_shas": int, "total_files": int}`; each group carries
`sha256`, `count`, and a list of `{name, directory}` locations (directory falls back to
`"(unknown)"`).

> `duplicate_files_report` lives **only** in `report_views.py`. The v4.00 document also
> described it under `views.py`; that duplicate entry was incorrect and has been
> removed.

## 5. ASGI / WSGI Strategy

Views are plain sync `def`. Under ASGI, Django wraps each sync view in
`sync_to_async(..., thread_sensitive=True)` automatically, which serializes it onto the
handler's dedicated thread — the same guarantee that makes Django ORM access safe. No
manual `sync_to_async()` calls are needed inside the views.

`download_file()` is the sole `async def` view. Inside it:

- the ORM lookup is wrapped explicitly: `await sync_to_async(FileIndex.get_by_sha256_for_download)(...)`
- file I/O uses `aiofiles` via `build_async_ranged_response()`

**Consequences of the sync conversion (v4.00 → v4.10):**

| v4.00 | v4.10 |
|---|---|
| `async_layout_manager()` | removed — call `layout_manager()` |
| `async_build_context_info()` | removed — call `build_context_info(sha, get_sort_param(request), show_dupes)` |
| `async_render()` in `views.py` and `report_views.py` | removed — call `django.shortcuts.render()` |
| `sync_to_async()` at every DB/FS boundary | only inside `download_file()` |

The project's ASGI safety rules still apply in full: never `thread_sensitive=False`
with the ORM, never `ThreadPoolExecutor` around ORM work.

## 6. Caching Architecture

| Cache | Location | Key | Backed by | Invalidated by |
|---|---|---|---|---|
| `layout_manager_cache` | `quickbbs.cache_registry` | `(page, dir.pk, sort, show_dupes)` | `MonitoredLRUCache` | `clear_layout_cache_for_directories()`, driven by `cache_watcher` |
| `distinct_files_cache` | `quickbbs.cache_registry` | `(directory, sort)` | `MonitoredLRUCache` | same |
| `all_files_shas_cache` | `quickbbs.cache_registry` | `(directory, sort)` | `MonitoredLRUCache` | same |
| `dir_counts_cache` | `quickbbs.cache_registry` | `directory` | `MonitoredLRUCache` | same |
| `sibling_dirs_cache` | `quickbbs.cache_registry` | `(parent_pk, sort)` | `MonitoredLRUCache` | same |
| `webpaths_cache` | `frontend.utilities` module level | `(full_path, directory)` | `MonitoredLRUCache` | Never (paths are stable) |
| `breadcrumbs_cache` | `frontend.utilities` module level | `uri_path` | `MonitoredLRUCache` | Never (paths are stable) |
| `_user_pref_cache` | `frontend.views` module level | `user.pk` | `ThreadSafeTTLCache` | `toggle_show_duplicates()` + TTL expiry |

`webpaths_cache` and `breadcrumbs_cache` are registered in
`cache_registry._MONITORED_CACHE_LOCATIONS`, so they appear in cache-statistics
snapshots alongside the central caches. `_user_pref_cache` is not registered.

`layout_manager` results do **not** include thumbnail state, so thumbnail generation
does not force a cache eviction.

**Thread safety:** because sync views execute across the ASGI handler's thread pool,
every shared cache must be thread-safe. `create_cache()` returns lock-guarded cache
objects, and `_user_pref_cache` uses `ThreadSafeTTLCache` rather than a bare
`cachetools.TTLCache`.

## 8. Directory Discovery Flow

When a request arrives for a URL that doesn't yet exist in `DirectoryIndex`:

```
_find_directory(paths)
    ├── normalize_fqpn(paths["album_viewing"])
    ├── DirectoryIndex.is_in_albums_tree(dirpath)   ← reject escapes, raise DirectoryInvalidError
    ├── get_dir_sha(dirpath)
    ├── search_for_directory_by_sha(sha)  →  not found
    ├── add_directory(dirpath)
    │   ├── physical path validation
    │   ├── parent directory creation (recursive)
    │   └── DB record creation
    ├── directory.parent_directory.invalidate_cache()  ← parent listing must show the new subdir
    ├── search_for_directory_by_sha(sha)               ← reload with prefetches
    └── update_database_from_disk(directory)           ← populate file entries
```

**Albums-root containment.** `normalize_fqpn()` resolves `..` segments and follows
symlinks, so a crafted URL — or a symlink placed inside the albums tree — could
otherwise escape the albums root. `is_in_albums_tree()` is checked *before* any
database work, and a rejection is logged with both the resolved and original paths and
raised as `DirectoryInvalidError` → HTTP 400.

**Race-condition check.** If the physical directory is missing at the post-lookup
`pathlib.Path(dirpath).exists()` check (present in DB but deleted from disk), the
parent and directory caches are both invalidated, `update_database_from_disk` is called
to clean up, and `DirectoryNotFoundError` is raised → HTTP 404.

Any other exception is logged and re-raised as `DirectoryInvalidError`.

## 10. Future Ideas

Directions under consideration. **Nothing here is committed or scheduled** — recorded
so the reasoning is not lost, not as a roadmap.

- **Blog support.** Authored/dated content alongside the gallery, rather than purely
  filesystem-derived listings.

  The raw capability already exists: HTML and Markdown files are recognized filetypes
  and are rendered as content, so semi-interactive pages can be built today simply by
  placing them in the albums tree. What is missing is the automation around them —
  ordering by date, indexes, navigation between entries, and the other conventions that
  make a set of documents read as a blog rather than as files that happen to be
  displayable.

  Note that Markdown is currently registered for `.markdown` only; `.md`, the more
  common extension, is not, and would need adding for this to feel natural in practice.
- **Scripting / interactive files.** A way for content in the tree to do something when
  viewed, adding interactivity beyond static display.
- **Uploads, with per-file ownership.** Prerequisite for accepting content through the
  application rather than out-of-band (§1.6).

The first two trace back to the QuickBBS lineage (§1.3): a bulletin board was a place
people *did* things, not only a place files were served from. These would bring some of
that back in an HTML-era form.

**Tensions to resolve first.** Each of these pushes against a current principle, and
none should be added without deciding the question deliberately:

- Blog posts kept as files in the albums tree stay inside the derivable-data rule
  (§1.1) — the post *is* the file. The tension appears only if posts acquire state the
  filesystem cannot express: authored-vs-modified dates independent of file
  timestamps, draft status, comments. Each of those must either be encoded in the file
  itself or become a deliberate exception alongside user accounts.
- Script state raises the same question more sharply, since anything a script
  accumulates while running is by definition not derivable from re-reading the tree.
- Uploads end the read-only posture (§1.1) and enlarge the threat model (§1.6). They
  require per-file ownership so each owner can manage their own files without affecting
  anyone else's — the reason they have been deferred rather than simply not built.

Separately, tagging, metadata, ratings, comments, and editing are considered useful but
unbuilt (§1.7); they are not listed here because they raise no principle conflict.
