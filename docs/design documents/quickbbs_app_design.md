## 1. Guiding Principles

This section explains *why* the `quickbbs` app is shaped the way it is. The sections
that follow describe *what* it does; nearly every mechanism below exists to serve one
of these principles. `quickbbs` is the layer that actually implements several
principles the `frontend` app only consumes — where they overlap, the wording here is
adapted to speak from the data layer rather than restated verbatim; see
[`frontend_design.md`](frontend_design.md) §1 for the product-level framing of the same
ideas.

### 1.1 The filesystem is the source of truth; the database is a cache

The founding idea, carried down from [frontend §1.1](frontend_design.md#11-the-filesystem-is-the-source-of-truth-the-database-is-a-cache).
At this layer it is implemented as literal state on every directory record: the
database holds nothing that cannot be regenerated by re-reading the filesystem, and
each record knows whether its own contents are still trustworthy.

- **The rule.** A directory record carries its own validity as part of itself — there
  is no separate tracking table alongside it. An invalidated record means "do not
  trust this record's file/subdirectory membership without rescanning first." A
  record is either in sync with disk or explicitly marked as not, with no third state.
  Marking a record invalid is deliberately not the same operation as deleting it.
  Deleting it would orphan every file underneath — and orphaning on suspicion, rather
  than on confirmed absence, creates its own mess: when the directory eventually gets
  rediscovered, there is no longer any record of which orphans actually belonged to it,
  versus files that were separately deleted from disk in the meantime. An invalidated
  record keeps that relationship intact while flagging it as unverified, so a rescan
  only has to reconcile membership, not first figure out what used to belong there.
- **Consequence: re-derivation is lazy, not scheduled — but nothing prevents scheduling
  it externally.** There is no built-in periodic background re-crawl of the whole tree
  — only the watchdog's live filesystem events and a page visit trigger a rescan by
  default. A built-in scheduled sweep would mean regularly walking a tree that, in the
  overwhelming majority of directories, has not changed since the last look — solving a
  failure mode (the watchdog missing something, or not running at all) that isn't the
  common case, at a cost paid on every directory whether or not anything ever happened
  there. The watchdog only runs inside the web server process, so a directory change
  made while the server is down would otherwise sit uncaught until someone happened to
  browse there. The `scan` management command exists precisely to cover that: its
  `--add_directories`/`--add_files`/`--verify_files` operations perform the same
  discovery/verification the watchdog and browsing trigger, `--start` scopes a run to a
  specific subtree rather than walking the whole database, and it is meant to be
  invoked externally — from cron, or from the tail end of a bulk file operation —
  whenever something changed the filesystem outside of a running, watching server. The
  laziness is a default, not a limitation; anyone who wants a scheduled sweep already
  has the tool to build one themselves, scoped to whatever they actually changed.
- **Consequence: invalidation propagates upward.** Adding, removing, or renaming
  something inside a directory invalidates that directory *and* every ancestor up to
  the albums root — a stale count or listing one level up is still a lie, even if the
  change happened several levels down. Invalidation is always a set of records, never
  a single one. This grew directly out of an earlier version of the gallery, where a
  change deep in the tree did not reliably surface in a parent's file/folder counts —
  the fix was to force every ancestor to re-evaluate rather than trust that "nothing
  changed in this directory itself" also meant "nothing changed that this directory
  displays." The cost is a rescan of directories that, in the common case, turn out
  unchanged; the alternative is a web page that is wrong until something else happens
  to evict the stale entry, and that trade is made deliberately in favor of the page
  being right.
- **Consequence: when the two disagree, the filesystem wins.** A record present in the
  database but missing from disk is deleted, not preserved as a question mark;
  filesystem entries with no matching record get one created on the next sync.
- **Consequence: caches must never outlive the truth.** Every cache that depends on
  directory or file membership — layout pages, distinct/all SHA lists, sibling
  ordering, subdirectory counts — is cleared through one shared invalidation path
  keyed on the directories that changed, so nothing downstream can go stale
  independently of the record it was derived from.

**Files are not deleted with their directory.** When a directory record is removed, its
files are not deleted alongside it — they lose their location and become legitimate
orphans instead, rather than having data destroyed that another lookup path might
still need. Orphaned records are reconciled later, not as an emergency cleanup.

### 1.2 A cache must never claim something doesn't exist

Every lookup cache in this app — directory-by-SHA, file-by-SHA, file-by-SHA-for-download
— caches a hit but never caches a miss. The thing being looked up (a directory, a file,
a thumbnail) can legitimately be created by a concurrent process moments after the
lookup that reported it missing. A cached "not found" would keep reporting that absence
until the entry aged out of the LRU, actively hiding work another part of the system
just finished. A false positive (serving something stale) is a correctness bug to fix;
a false negative that outlives its own cause is worse, because nothing signals that it
needs fixing — the cache is just quietly wrong until enough unrelated traffic evicts it.

### 1.3 Identical files are the same file

Carried down from [frontend §1.2](frontend_design.md#12-identical-files-are-the-same-file).
At this layer, identity is content, not a record's location: the same bytes appearing
in ten directories are ten file records sharing one identity, not ten independent
files. This is where the idea originates, not just where it is implemented — content
identity exists first to answer "is this a duplicate," so the same thumbnail and
derived work is never generated twice for bytes already processed elsewhere.

A second, separate identity — content plus its specific path — exists alongside the
content-only one so that the two different questions this raises can both be answered:
scanning by the content-only identity finds every duplicate of a file, while the
combined identity picks out one specific copy at one specific location, which is what
downloads and navigation need. Deduplication and per-location addressing are different
problems, and the data model keeps them as two separate identities rather than
collapsing them into one.

**The combined identity is also what makes a file identifiable independent of a
database that might not survive.** A prior design (an assigned identifier disconnected
from either the file or its path) meant regenerating the database after data loss
produced fresh identifiers — the fix was already necessary once, since the database
really was lost once, while writing test code. But the further motivation for shifting
to a computed identity was reliable benchmarking: a randomly generated identifier is
only as stable as the row it lives in, so a benchmark script that hardcodes one is
gambling on that row surviving unchanged. A computed identity is stable by
construction — once a file is in the database, its identifier is fixed past, present,
and future, because it is derived from the file itself rather than assigned to it. A
benchmark script can hardcode that identifier once and trust it indefinitely, at the
cost of computing a hash for every file, which is the more expensive side of that trade
for very large files.

### 1.4 Read-only keeps the threat model small

Carried down from [frontend §1.6](frontend_design.md#16-read-only-keeps-the-threat-model-small).
At this layer it shows up as a single chokepoint: every path that can create a
directory record — filesystem sync, watchdog-driven discovery, `.link`/`.alias`
resolution, management commands — funnels through one shared creation routine, and
that is the one place paths outside the albums root are rejected. There is no second
way to create a directory record that bypasses the check.

### 1.5 Scope is set by real use, not feature parity

Carried down from [frontend §1.7](frontend_design.md#17-scope-is-set-by-real-use-not-feature-parity).
The data model already reserves schema for a permissions and favorites system that has
not been built yet — placeholders, not a promise of imminent delivery. Read their
presence as a marker of direction, not as in-progress work.

The same principle governs which file formats are recognized. Format support has grown
one type at a time, each added because it was content that actually needed to be
displayed, never against a target list of formats to eventually cover. Nothing has
been deliberately excluded — there is no format ruled out on principle, only formats
not yet encountered. This is workable specifically because filetype recognition is
modular: adding one is a contained change, not a redesign, so there has been no
pressure to front-load support for formats that aren't in use yet.

## 2. Purpose

The `quickbbs` package is the **core domain layer** of the QuickBBS gallery
application. It owns:

- **The two primary ORM models** (`DirectoryIndex`, `FileIndex`) that represent the
  complete gallery index, including their filesystem-synchronization and
  cache-invalidation methods
- **The central cache registry** — the shared LRU/TTL caches used across the app
  boundary and the single function that clears them together
- **Shared utility primitives** — hashing, path normalization, sort matrices, a
  thread-safe cache implementation, a parallel-hashing thread pool
- **Background tasks** — thumbnail generation, database maintenance, SSL certificate
  monitoring, and cache-statistics snapshotting
- **Django project configuration** — settings, URL routing, ASGI/WSGI entry points,
  and process-startup checks

Every other Django app (`cache_watcher`, `filetypes`, `frontend`, `thumbnails`,
`user_preferences`) depends on `quickbbs`; `quickbbs` depends on `filetypes` and
`thumbnails` only, and then only at function-call time using deferred imports to break
circular dependency chains.

## 4. Component Reference

### 4.1 `models.py`

**What does this do?** Lets other code write the ordinary `from quickbbs.models
import DirectoryIndex, FileIndex` even though neither class is actually defined in
this file.

**What is its purpose?** The single import point external code uses:
`DirectoryIndex` and `FileIndex` are defined in `directoryindex.py` and `fileindex.py`
respectively, and `models.py` imports and re-exposes both from one place.

`DirectoryIndex` and `FileIndex` mutually reference each other, and `cache_registry.py`
needs both — a genuine three-way import cycle, not an accident of file organization.
`models.py` breaks it by defining `Owners` and `Favorites` first (satisfying
`FileIndex`'s FK to `Owners`), then importing and re-exporting `DirectoryIndex` and
`FileIndex` at the bottom of the file, after their class bodies exist. See §6 for the
full cycle across all three files.

### 4.2 `directoryindex.py`

**What does this do?** Keeps track of every directory in the gallery, and whether
what the database knows about that directory's contents still matches what's on disk.

**What is its purpose?** Defines `DirectoryIndex`, the master index for gallery
directories: one row per unique filesystem path under the albums root.

#### Fields

| Field | Type | Notes |
|---|---|---|
| `fqpndirectory` | `CharField(unique)` | Fully-qualified normalized path — always lowercase |
| `dir_fqpn_sha256` | `CharField(unique)` | SHA256 of `fqpndirectory` — primary lookup key |
| `parent_directory` | `FK(self, SET_NULL)` | Self-referential parent link; `None` for the albums root |
| `lastscan` | `FloatField` | Unix timestamp of last filesystem sync |
| `lastmod` | `FloatField` | mtime from OS `stat()` |
| `cache_invalidated` | `BooleanField(default=True)` | `True` = contents need rescanning before they can be trusted |
| `cache_lastscan` | `FloatField(default=0)` | Unix timestamp of the last scan or invalidation write |
| `name_sort` | `NaturalSortField` | Auto-computed natural-sort key over `fqpndirectory` |
| `is_generic_icon` | `BooleanField` | `True` if no real cover image is available |
| `delete_pending` | `BooleanField` | Soft-delete flag; row excluded from all queries |
| `filetype` | `FK(filetypes, ".dir")` | Always the `.dir` filetype entry |
| `thumbnail` | `FK(FileIndex, SET_NULL)` | The cover-image file for this directory |

**Database indexes:** `(parent_directory, delete_pending)` and
`(dir_fqpn_sha256, delete_pending)` composite indexes, plus a `GinIndex` trigram index
on `fqpndirectory` backing search's `iregex`/`icontains` lookups (previously a ~108ms
sequential scan over the full table).

`cache_invalidated` and `cache_lastscan` carry no index at all — the row is always
reached via `dir_fqpn_sha256` or its primary key, and an unindexed boolean lets
watchdog-driven updates qualify for Postgres's heap-only-tuple optimization instead of
paying index-maintenance cost on every scan.

**Reverse relationships:** `parent_dir` (self, via `parent_directory`),
`FileIndex_entries` (from `FileIndex.home_directory`), `Virtual_FileIndex` (from
`FileIndex.virtual_directory`).

#### `update_database_from_disk(directory_record)`

**What does this do?** Makes sure what a directory's page shows matches what is
actually on disk, without paying the cost of checking the filesystem on every single
visit.

**What is its purpose?** Top-level filesystem-sync entry point — called by the gallery
view on a cache miss and by management commands — that reconciles one directory's
database rows against its on-disk state.

Turns one directory's on-disk state into the matching set of database rows, but only
when the row's own cache state says it is out of date. A directory whose
`cache_invalidated` flag is already `False` returns immediately without touching the
filesystem — the common case for a page someone is actively browsing. When a rescan is
needed, the record is reloaded from the database first (the watchdog may have flipped
the flag between when this object was loaded and now, and re-checking after reload
catches a race where invalidation and revalidation land back-to-back).

**Flow:**

```
update_database_from_disk(directory_record)
    ├── is_in_albums_tree() guard        ← refuse to sync an out-of-tree legacy row
    ├── is_cached short-circuit          ← already valid, nothing to do
    ├── refresh_from_db()                ← catch a concurrent watchdog invalidation
    ├── is_cached re-check               ← re-validated during the reload race window
    ├── return_disk_listing_sync(dirpath)
    │   └── not found → handle_missing() ← directory vanished; delete row, invalidate parent
    ├── sync_subdirectories(fs_entries)
    ├── sync_files(fs_entries, bulk_size)
    ├── mark_scanned()                   ← cache_invalidated=False, fresh cache_lastscan
    └── close_old_connections()
```

---

#### `sync_subdirectories(fs_entries)`

**What does this do?** Keeps a directory's list of subfolders honest — adds the ones
that showed up on disk, drops the ones that vanished, and refreshes the ones whose
timestamps changed.

**What is its purpose?** Reconciles a directory's immediate `DirectoryIndex` children
against the filesystem entries passed in.

Changed `mtime` triggers a `bulk_update` under `SELECT FOR UPDATE (skip_locked)` to
avoid racing a concurrent sync of the same rows. Directories on disk but not in the
database are created one at a time through `add_directory()`, since that function's own
parent-chain recursion makes a bulk-insert path impractical. Directories in the
database but gone from disk are deleted outright.

---

#### `sync_files(fs_entries, bulk_size)`

**What does this do?** Keeps a directory's list of files honest, the same way
`sync_subdirectories` does for folders, but cheaply enough to run on every rescan of a
directory with thousands of files.

**What is its purpose?** Reconciles a directory's `FileIndex` rows against the
filesystem entries passed in, using a two-stage change-detection pass in front of the
usual create/update/delete reconciliation.

Stage 1 pulls a plain `.values()` dict per matched file — no ORM object, no joined
relations — and checks it against the filesystem `stat()` result; only rows that stage 1
flags as possibly different go on to stage 2, where a full `FileIndex` object is loaded
and `check_for_updates()` decides what actually changed. Files that already match on
disk never pay the cost of full object instantiation. New files get their SHA256 hashes
computed in parallel via `_batch_compute_file_shas()` once a batch crosses
`SHA256_PARALLEL_THRESHOLD`; missing files are marked `delete_pending=True` rather than
deleted immediately.

#### Cache invalidation

The methods that keep `cache_invalidated` honest, and propagate that dishonesty
upward when it needs to.

| Method | Type | Description |
|---|---|---|
| `is_cached` | `@property` | Reads `not self.cache_invalidated` directly — no query |
| `mark_scanned()` | instance | Marks this row valid: `cache_invalidated=False`, fresh `cache_lastscan` |
| `cache_valid_for_sha(sha256)` | `@staticmethod` | Existence check for a valid (non-invalidated) directory by SHA |
| `invalidate_cache()` | instance | Single-directory invalidation: clears thumbnail, flips the flag, clears layout caches |
| `invalidate_cache_by_sha(sha256)` | `@staticmethod` | Look up by SHA, then delegate to `invalidate_cache()` |
| `invalidate_caches(index_dirs)` | `@staticmethod` | Batch entry point — expands to parents, delegates to `_invalidate_by_shas()` |
| `invalidate_all_caches()` | `@staticmethod` | Marks every row invalidated; used for a full forced rescan |

`invalidate_caches()` and its underlying `_invalidate_by_shas()` are the propagation
path described in §1.1: given a set of changed directories, they first expand that set
to include every ancestor up to the albums root (`get_all_parent_shas()`), then issue
one bulk `UPDATE` and one call to `clear_layout_cache_for_directories()` covering the
whole expanded set. A change three levels deep invalidates all three levels, not just
the leaf.

#### `files_in_dir(sort, distinct, additional_filters, fields_only, select_related)`

**What does this do?** Returns the files in a directory, optionally collapsing
duplicate copies of the same content down to one entry per unique file — the choice a
gallery page or the item-view show/hide-duplicates toggle needs to make.

**What is its purpose?** File queryset for a directory; `distinct=True` deduplicates by
`file_sha256` via a two-query dedup, not a Python re-sort.

PostgreSQL `DISTINCT ON` requires `file_sha256` to lead the `ORDER BY`, which would
disrupt the caller's requested sort order. Rather than fetch the deduplicated rows and
re-sort them in Python, a first query computes just the deduplicated primary keys as a
subquery (`_distinct_file_pks()`), and a second query wraps that subquery with the
caller's actual sort order — one round trip, no intermediate list of Python objects.
Staying inside PostgreSQL for both the dedup and the final sort matters because
Python's ASCII collation (`'-' < '_'`) and PostgreSQL's `en_US.UTF-8` collation
(`'_' < '-'`) disagree: a Python-side re-sort would order files differently than the
database does, so the gallery listing and item-view navigation could show the same
directory's files in two different orders.

---

#### `find_by_physical_path(physical_path)`

**What does this do?** Lets a `.link` shortcut or macOS alias that points at a file on
some other volume find its way back to the matching directory inside the gallery,
instead of just failing when the target isn't a gallery path.

**What is its purpose?** Resolves a physical (drive-level) path to its corresponding
`DirectoryIndex` gallery directory. Never trusts a bare basename: resolution tries, in
order, a direct lookup if the path is already under the albums root; an explicit
`settings.ALIAS_MAPPING` override, matched by longest prefix; and finally a
longest-suffix match against existing `DirectoryIndex` rows, which stops once only two
trailing path components remain — a single-component match was validated against all
474 production aliases (2026-07-07) and every one that looked "unique" actually linked
the wrong directory when the real gallery copy was missing.

### 4.3 `fileindex.py`

**What does this do?** Keeps track of every file in the gallery, including which ones
are byte-identical to each other, so duplicate copies never need separate thumbnails
or separate identity.

**What is its purpose?** Defines `FileIndex`, the master index for all gallery files:
one row per unique file location.

---

#### Fields

| Field | Type | Notes |
|---|---|---|
| `file_sha256` | `CharField` | SHA256 of file content; not unique — identical files share one value |
| `unique_sha256` | `CharField(unique)` | SHA256 of content + title-cased path; the stable external identifier |
| `lastscan` | `FloatField` | Unix timestamp of last sync |
| `lastmod` | `FloatField` | mtime from OS `stat()` |
| `name` | `CharField` | Title-cased filename |
| `name_sort` | `NaturalSortField` | Auto-computed natural-sort key over `name` |
| `duration` | `BigIntegerField` | Video duration in milliseconds; `NULL` for non-video |
| `size` | `BigIntegerField` | File size in bytes |
| `home_directory` | `FK(DirectoryIndex, SET_NULL)` | Physical parent directory |
| `virtual_directory` | `FK(DirectoryIndex, SET_NULL)` | Target directory for `.link`/`.alias` shortcut files |
| `is_animated` | `BooleanField` | `True` for animated GIFs |
| `ignore` | `BooleanField` | Excluded from gallery display |
| `delete_pending` | `BooleanField` | Soft-delete flag |
| `cover_image` | `BooleanField` | Marks this file as its directory's cover image |
| `filetype` | `FK(filetypes, ".none")` | Extension lookup; CASCADE-deletes if the filetype is removed |
| `is_generic_icon` | `BooleanField` | `True` if the thumbnail is the filetype fallback icon |
| `new_ftnail` | `FK(ThumbnailFiles, SET_NULL)` | Link to the generated thumbnail record |
| `ownership` | `OneToOne(Owners)` | Per-file ownership — reserved for the future permissions system (§1.5) |

**Database indexes:** a partial `(file_sha256, delete_pending)` index, a `name` btree
index plus a `name` trigram `GinIndex`, `(filetype, delete_pending)`, a partial index
on `file_sha256` where `new_ftnail` is null (unlinked-thumbnail lookups), a composite
`(home_directory, filetype, delete_pending)` index, and a partial index on `id` where
`delete_pending=True`. The set was pruned on 2026-07-04 against production
`pg_stat_user_indexes` evidence — several previously-listed indexes (on `name` alone,
on `unique_sha256` combined with `delete_pending`, on `home_directory` combined with
`delete_pending`) were removed as never or rarely scanned in practice.

**Why two SHA256 fields.** `file_sha256` identifies identical content wherever it
appears (§1.3). `unique_sha256` identifies one specific copy at one specific path, and
is what every external URL uses — it is regenerable from content and path alone, unlike
the UUID primary key it replaced, which was random and unrecoverable after a row was
deleted and recreated.

**Class-level caches:** `_encoding_cache` (avoids re-detecting text encoding on repeat
reads of the same file) and `_alias_cache` (caches resolved macOS `.alias` targets).

| `link_to_thumbnail(file_sha256, thumbnail)` | `@classmethod` | Links every unlinked `FileIndex` row sharing a SHA to a generated thumbnail record |
| `set_generic_icon_for_sha(sha, is_generic)` | `@classmethod` | Shared setter for `is_generic_icon` across every copy of a file |

**The three `*_by_sha` duplicate-lookup statics above are prototypes, not dead code** —
written to validate identity/duplicate-detection approaches during development, kept
for a possible future use, with no current production caller. Same status as
`get_file_counts()`/`get_count_breakdown()` on `DirectoryIndex` (§4.2).

**Link file format (`.link`).** The filename itself encodes the target:
`<display_name>*<path_with_slashes_as_underscores>.link` — e.g.
`Paris Trip*albums__2024__paris.link` resolves to `/albums/2024/paris/`.

#### `check_for_updates(fs_entry, home_directory, fs_stat=None, precomputed_sha=None)`

**What does this do?** Decides whether one file's database record has fallen out of
sync with the actual file on disk, and if so, brings it back in line — without
re-hashing every file on every scan just to be sure.

**What is its purpose?** Compares a `FileIndex` record against its matching filesystem
entry (mtime, size, link target, animated-GIF flag, movie duration) and applies any
detected drift onto the in-memory record.

Change detection here is a deliberate tradeoff, not an oversight: SHA256 is only
recomputed when a record has none at all — a content edit that preserves name, size,
and modification time updates `lastmod`/`size` on the next sync but leaves
`file_sha256`/`unique_sha256` untouched, so SHA-keyed features (thumbnails, duplicate
detection) will not notice it. Detecting that case would mean rehashing every file on
every sync regardless of whether anything actually looks different — full
antivirus-grade tamper detection, at a cost the gallery does not need to pay. The
watchdog still sees the underlying filesystem write and forces a rescan of the
directory; what it does not force is a SHA recompute for a file whose observable
attributes didn't change. Reproducing that exact scenario requires filesystem-level
access and deliberate effort to hold size and mtime constant — usability and
performance win over closing a gap that narrow. Pinned by a test
(`test_sync.py::test_modified_file_updated_in_place`) so the behavior stays intentional
rather than silently regressing.

### 4.4 `cache_registry.py`

**What does this do?** Gives every app a shared place to keep caches without any of
them having to import each other just to invalidate one.

**What is its purpose?** Houses the shared caches that span app boundaries, and the
one function that clears them together.

Cache objects and their invalidation live here rather than in `frontend`, specifically
so `cache_watcher`, `thumbnails`, and `frontend` can all import them without any of
those apps having to import each other — placing them in `frontend` would force
`cache_watcher` to depend on `frontend`, which is the dependency direction the app
boundaries are meant to prevent.

---

#### `clear_layout_cache_for_directories(directory_ids)`

**What does this do?** Makes sure that once a directory's contents change, every page
and list that was built from the old contents gets thrown away instead of continuing to
show something stale.

**What is its purpose?** The single function that clears `layout_manager_cache`,
`distinct_files_cache`, `all_files_shas_cache`, `dir_counts_cache`, and
`sibling_dirs_cache` together for one or more directories.

It is the mechanism behind §1.1's "caches must never outlive the truth" — every caller
that changes what a directory contains (the watchdog, `bulk_sync()`, thumbnail
generation) reaches this one function rather than clearing caches individually, so
there is exactly one place that can get the invalidation set wrong.

Two of the five caches it clears use different key-construction strategies, driven by
what each cache actually needs to invalidate by:

- **`distinct_files_cache` and `all_files_shas_cache`** are keyed by
  `hashkey(directory_instance, sort)`. Django model instances hash by primary key, so a
  bare `DirectoryIndex(pk=pk)` stub — no fields loaded — matches the cached entry for
  the real object, avoiding a full object load just to construct an invalidation key.
- **`layout_manager_cache`** is keyed by `hashkey(page_number, directory_pk, sort,
  show_duplicates)`. Page number is unbounded, so no fixed set of keys could ever be
  constructed for a directory; invalidation instead scans every live key and removes
  the ones whose directory matches.

### 4.5 `MonitoredCache.py`

**What does this do?** Lets every cache in the app be touched from any thread —
watchdog threads, timer threads, task threads, request threads — without any of them
having to coordinate with each other first.

**What is its purpose?** Every cache in this app is safe to call from threads that
have never coordinated with each other, because that is the actual situation the
caches live in: watchdog observer threads, debounce timer threads, task-runner
threads, and web request worker threads all touch the same cache objects, and
`cachetools` itself is explicit that it does *not* handle that — synchronization is
the caller's responsibility.

Rather than push that responsibility onto every call site, `_ThreadSafeCacheMixin`
wraps every primitive (`__getitem__`, `__setitem__`, `__delitem__`, `__contains__`,
`__len__`, `__iter__`) and every compound check-then-act operation (`get`, `pop`,
`setdefault`, `popitem`, `clear`) behind a single reentrant lock. The compound
operations matter as much as the primitives: two threads calling `pop(key, None)`
concurrently against an unlocked cache can both find the key present, after which the
loser raises `KeyError` despite having supplied a default — locking only the
primitives would not prevent that.

`create_cache(maxsize, name, monitored)` is the factory every cache in the app goes
through: `ThreadSafeLRUCache`/`ThreadSafeTTLCache` when monitoring is off,
`MonitoredLRUCache` (same locking, plus hit/miss counters) when
`settings.CACHE_MONITORING` is `True`.

**Why two variants exist, not just one.** `MonitoredLRUCache` is a tuning tool, not a
production feature. Every cache in the app (`fileindex_cache`, `directoryindex_cache`,
`layout_manager_cache`, and the rest) has a fixed `maxsize` set in
`quickbbs_settings.py`, and there is no way to know whether that number is right — too
small, and the cache evicts entries it will need again moments later, paying to
recompute what it just threw away; too large, and it holds memory the working set
never actually needs — without watching real hit/miss behavior under real traffic.
`MonitoredLRUCache` answers that question: it wraps `ThreadSafeLRUCache` and adds
exactly one thing, a hit/miss counter incremented on every lookup (`self.hits += 1` /
`self.misses += 1` in `__getitem__`), exposed through `.stats()` and `.hit_rate`.

**Reading the hit rate requires knowing which of two causes a miss actually is.** A
low hit rate has two unrelated possible explanations, and the module's own docstring
comment states only the first as if it always applies:

- **Eviction-driven misses — `maxsize` actually is too small.** A key that was cached,
  then evicted to make room for newer entries, then requested again shortly after —
  this is the case a bigger `maxsize` fixes, because the same key really is being
  reused; it's just not staying resident long enough to be there for the second ask.
- **Cold-key misses — no `maxsize` would help.** A workload where most keys are
  genuinely one-shot (e.g. `fileindex_cache` during a bulk import touching thousands of
  distinct files once each) will show a low hit rate no matter how large `maxsize` is,
  because the same key is never asked for twice — there is nothing to retain.

The hit-rate number alone doesn't distinguish these. A low rate is only a signal to
grow `maxsize` when the workload is known to be repetitive (the same directories,
files, or paths getting revisited, as gallery browsing typically is) — for a
one-shot-heavy workload, a low hit rate is simply what correct behavior looks like, and
growing the cache would just hold more memory for keys that were never coming back
anyway. A consistently high hit rate against a large `maxsize`, on the other hand, is a
safer signal in both cases — it means the cache could likely be shrunk without losing
hits.

**The admin console does this comparison for you.** Reading hit rate and `maxsize`
side by side and reasoning through which of the two causes applies is exactly the
kind of thing a person tuning a cache shouldn't have to redo by hand every time. The
`cache_watcher` app's admin page for `CacheStatisticsTracking`
([`cache_watcher_design.md` §4.7](cache_watcher_design.md#47-adminpy)) adds a
**Sizing Advice** column that runs this same eviction-vs-cold-key check against each
cache's `current_size` and `max_size` from its latest snapshot, and prints a short
verdict — "Full + low hit rate — consider raising `X_CACHE_SIZE`," "Low hit rate but
cache isn't full — likely one-shot traffic," "Healthy, oversized — could shrink," or
"Not enough traffic yet" when there's too little data to read at all (`hits + misses`
under 50). It's a suggestion, and should be treated like one: a sheer mechanical
calculation from one snapshot, not a decision. If performance already seems fine,
take its advice with a grain of salt.

**The cost of monitoring is real but small, and it is not paid once you turn
monitoring off.** The counter increment happens on every single cache read, so it is
not free — but it is one integer increment per lookup, not an extra lock, an extra
query, or any I/O; `MonitoredLRUCache` reuses the exact same
`_ThreadSafeCacheMixin`-based locking as `ThreadSafeLRUCache`; only the counter is
added on top. This is why the two classes coexist instead of one always-monitored
cache: monitoring is deliberately opt-in, controlled by the single
`settings.CACHE_MONITORING` flag in `quickbbs_settings.py` (`create_cache`'s
`monitored` argument is always passed as `monitored=settings.CACHE_MONITORING`, at
every call site in the app — there is no cache that hardcodes its own answer). With
`CACHE_MONITORING = True`, every cache in the app is the counting variant, ready for a
tuning session; set it back to `False` and every cache reverts to the plain
`ThreadSafeLRUCache`/`ThreadSafeTTLCache`, which has no counter to increment at all —
the workflow is turn monitoring on, run the gallery under a representative workload,
read the hit rates, adjust `*_CACHE_SIZE` settings as needed, then turn monitoring back
off so the always-on production path never pays for statistics nobody is currently
watching.

### 4.6 `common.py`

**What does this do?** Gives the rest of the app one place to hash a file, normalize
a path, or get a consistent sort order, instead of every module reimplementing its own
version.

**What is its purpose?** A common location for routines shared across sub-applications
— hashing, path normalization, and sort ordering — so `frontend` and `cache_watcher`
both call the same implementation rather than each maintaining their own.

**Two sort matrices, for two different query shapes.** `SORT_MATRIX` handles mixed
directory-and-file queries and joins to `filetypes` so directories consistently sort
first. `DIR_SORT_MATRIX`, used by `dirs_in_dir()`, omits that join entirely — every row
it queries already has `filetype=".dir"`, so a `filetype__is_dir` field would be
constant across the whole result set, and joining to test a constant wastes a join.

**Parallel SHA256 hashing uses a thread pool, not a process pool, deliberately.**
`get_file_sha()` never touches the Django ORM, so the usual thread-safety concern
around parallelizing database work doesn't apply here. The choice is forced the other
way: `_batch_compute_file_shas()` runs from daemon threads in the ASGI `sync_to_async`
context, and `ProcessPoolExecutor` cannot spawn child processes from a daemon thread —
`ThreadPoolExecutor` is the only one of the two that works in that context at all. The
pool is a lazily-initialized module-level singleton so repeated calls reuse warm
threads instead of paying spawn overhead each time, and it registers its own `atexit`
shutdown.

**`normalize_string_lower()` and `normalize_string_title()` share one cache but not one
keyspace.** Both are backed by `normalized_strings_cache`, but `cachetools` keys purely
on function arguments — a bare `hashkey(s)` would let whichever function ran first for
a given string silently poison the result for the other. Each function's `@cached` key
is namespaced (`hashkey("lower", s)` / `hashkey("title", s)`) so the shared cache never
crosses the two.

### 4.7 `tasks.py`

**What does this do?** Runs the maintenance work a gallery needs periodically —
thumbnail catch-up, database vacuuming, certificate expiry checks — without making a
web request wait for any of it.

**What is its purpose?** All tasks use the `django-dbtasks` backend (`@task()`
decorator), executed by a separate `python manage.py taskrunner` process. Not every
function in this module is a task — several are plain helpers called both by a task
and, in one case, directly at server startup.

| Function | Decorated? | Description |
|---|---|---|
| `generate_missing_thumbnails(shas, directory_pk, batch_size)` | `@task()` | Batch thumbnail creation: pre-filters SHAs that already have thumbnails, generates the rest, bulk-writes, clears the directory's layout cache |
| `get_vacuum_candidates(scale_factor_threshold, min_live_rows)` | plain | Queries `pg_stat_user_tables` for tables whose dead-tuple ratio exceeds a threshold; empty list on non-Postgres backends |
| `vacuum_table(table_name)` | plain | Runs `VACUUM ANALYZE` on one table, toggling autocommit since `VACUUM` cannot run inside a transaction |
| `weekly_vacuum_check()` | `@task()` | Periodic (Sundays): finds and vacuums bloated tables via the two functions above |
| `get_ssl_cert_status(cert_path)` | plain | Reads certificate expiry via `cryptography.x509`; returns `None` when no certificate is configured |
| `check_ssl_cert_expiry()` | `@task()` | Periodic (daily, 6am): logs an error/warning based on certificate status; also invoked directly from `apps.py` at process startup |
| `daily_cleanup_finished_jobs()` | `@task()` | Periodic (daily, midnight): deletes old `ScheduledTask` rows as a safety net for records the runner's own cleanup loop missed |
| `snapshot_cache_statistics()` | plain | Writes current hit/miss counters from every `MonitoredLRUCache` to the database |

**Thumbnail priority convention:** web-request-triggered generation enqueues at
priority 50; bulk maintenance (`--add_thumbnails`) enqueues at priority 0 — a higher
number is processed first, so a gallery someone is actively looking at is served ahead
of background catch-up work.

**`snapshot_cache_statistics()` must run inside the web server process.** It reads
in-memory counters directly off live cache objects; called from a separate
`taskrunner` process it would see freshly-initialized, zero-count caches instead. It is
called from `view_gallery()` on gallery requests when `CACHE_MONITORING` is enabled,
but throttled to at most once per `SNAPSHOT_MIN_INTERVAL` seconds via a module-level
monotonic timestamp — the underlying counters are cumulative, so a throttled call loses
no data, only some freshness in the database row, and rows whose stats haven't changed
since the last snapshot are skipped entirely to avoid a write with nothing new to say.

### 4.8 `apps.py`

**What does this do?** Does the one-time setup a running server needs at boot, while
making sure that setup never accidentally runs during a management command or a
dev-server reloader's parent process.

**What is its purpose?** Defines `QuickbbsConfig`, which runs once-per-process
startup work from `ready()`, gated so it only fires for the actual server process —
not for `migrate`, `shell`, `scan`, or other management commands, and not for the
Werkzeug/runserver_plus parent process when the dev server reloader spawns a child.

Two things happen here specifically because `ready()` is the last point in Django's
startup sequence where they can be done deterministically:

- **Re-registering `ScheduledTask`'s admin.** `django.contrib.admin`'s autodiscovery
  imports `quickbbs.admin` before `dbtasks.admin` (an artifact of `INSTALLED_APPS`
  order), so `dbtasks`'s own admin registration always wins if `quickbbs` tries to
  register a custom one directly in `admin.py`. `AppConfig.ready()` runs after all
  admin autodiscovery has finished, so re-registering there wins regardless of app load
  order.
- **Checking SSL certificate expiry at startup**, by calling
  `quickbbs.tasks.check_ssl_cert_expiry.func()` directly — the same logic that backs
  the daily periodic task, so there is one implementation of "is the certificate okay"
  rather than two that could drift apart.

## 6. Circular Dependency Map

`DirectoryIndex`, `FileIndex`, and `models.py` form a genuine three-way mutual
dependency, handled with deferred imports rather than restructured away:

```
models.py
  └── imports from directoryindex.py (bottom of file, after class bodies)
  └── imports from fileindex.py      (bottom of file, after class bodies)

directoryindex.py
  └── imports from cache_registry.py  (after module-level cache creation)
  └── imports from fileindex.py       (FILEINDEX_SR_FILETYPE — after cache init)
  └── imports DirectoryIndex/FileIndex cross-references inside methods (deferred)

fileindex.py
  └── imports Owners from models.py   (after module-level code, before class body)
  └── imports from directoryindex.py  (deferred, inside methods)
  └── imports clear_layout_cache_for_directories from cache_registry.py (deferred, inside methods)
```

**Rule:** no cross-model import at module top level. Every
`DirectoryIndex`↔`FileIndex` reference used only for type annotations goes inside a
`TYPE_CHECKING` block; every reference needed at runtime is an import placed either
after the point in the file where the cycle is broken, or deferred entirely inside the
function that needs it.
